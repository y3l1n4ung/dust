# Server Plugin Design

Status: proposal, with the runtime built. This document describes a Dust feature
for generating Dart HTTP server wiring from annotated controller classes, with
runtime route composition.

`packages/dust_server` exists and is covered by over 1,200 tests at 100% line
coverage, including `test/generated/`, which hand-writes what the plugin will
emit for the [Worked Example](#worked-example) below, and 51 examples in
`example/` that exercise every extractor, layer, and response path the plugin
will emit against.

The package is unpublished (`publish_to: none`); no plugin crate exists yet.
Sections marked **runtime-checked** describe behavior that runs today rather
than intent — and that distinction earned its keep: writing those examples turned
up sixteen defects in the runtime, which is sixteen the generated code would
otherwise have been built on top of.

For the build pipeline and crate map, see the [Developer Guide](../developer.md).
For the plugin contract, see the [Plugin Guide](../plugin-guide.md).
For the runtime as it exists today, see [dust_server](../dust_server/README.md).

## Goals

- Generate request decoding, parameter extraction, validation, response
  encoding, and route registration from ordinary Dart classes.
- Keep handler bodies handwritten. Dust owns wiring, never business logic.
- Reuse existing Dust features: `Serialize`/`Deserialize` for payloads,
  `Validate` for request bodies, `Result`/`Option` from `dust_dart/fp.dart`.
- Keep the mount tree inspectable, so API documentation can be generated by a
  separate package instead of being baked in.
- Keep one annotation per declaration. Configuration goes in annotation
  arguments, not in stacked annotations.
- Take the extractor taxonomy from axum: the same built-in set, the same
  rejection status codes, the same body-versus-parts split.

## Non-goals

- API documentation. Deferred to a separate package; see
  [API documentation, deferred](#api-documentation-deferred).
- A dependency-injection container. Controllers are constructed with plain Dart
  constructors at the composition site. Axum's `State<S>` has no annotation
  here; it is a `final` field on the controller.
- Replacing `shelf`. Generated code targets the standard `Handler` contract and
  composes with existing `shelf` middleware.

## Naming

The package is `dust_server`, not `dust_shelf` or `dust_api`.

`shelf` is not a swappable driver in the sense that `sqlite3` is. Its
`Handler` typedef is the interoperability contract that other Dart server stacks
already accept, so naming the package after it would name the substrate rather
than the capability. `dust_api` collides with existing vocabulary: the HTTP
client guide already names its example class `UserApi`.

The existing HTTP client sets the precedent. It is Dio-specific but ships as
`package:dust_dart/http.dart`, named for the capability.

## Package and Crate Layout

| Path | Responsibility |
| :--- | :--- |
| `packages/dust_server` | Annotations, `FromRequestParts`, `Router`, `Rejection`, `IntoResponse`, `Layer`, `MountedRoute`, the shipped layers, and `serveRouter`. |
| `crates/dust_server_plugin` | `DustPlugin` implementation. |
| `crates/dust_ir/src/server.rs` | `ServerIr`, matching the existing `http.rs`, `route.rs`, `db.rs` split. |

`dust_server` depends on `dust_dart`, `shelf`, `mime`, and `meta`. Routing is
its own, so `shelf_router` is not a dependency.

> [!IMPORTANT]
> Server annotations must not go in `dust_dart`. `dust_flutter` depends on
> `dust_dart`, so adding `shelf` there would pull server dependencies into every
> Flutter application.

`dust_server/server.dart` re-exports `shelf`'s `Request`, `Response`,
`Middleware`, `shelf_io.serve`, and `dust_dart/fp.dart`, so applications need
one import.

## Engine Prerequisites

None blocking. Every phase below builds against today's parser, resolver, and
IR.

### Cleared: class interfaces in IR

`ClassIr` records `superclass_name: Option<String>` and `is_interface`, but no
`implements` clause (`crates/dust_ir/src/class.rs`), and `implements` appears
nowhere in `dust_parser_dart` or `dust_parser_dart_ts`. An earlier revision of
this design needed it to bind an extractor to its value type across files.

Naming the extractor **type** at the call site removes that need. `@Extract`
supplies the extractor type, the parameter's own type supplies the value type,
and the generated cast makes `dart analyze` verify they agree. Dust never
resolves the binding, so it never needs the interface list.

The remaining users of an `implements` list are `IntoResponse` and `Validatable`
dispatch, and both detect structurally from `MethodIr` instead — the same
approach the serde plugin already takes for `toJson` and `fromJson`
(`crates/dust_plugin_serde/src/analysis.rs`), accepting the same small
false-positive risk. Structural, from the IR: nothing here reflects at runtime.

Adding `ClassIr.interfaces` remains an improvement for the codebase as a whole;
it would replace that structural detection and unlock the bare-type extractor
form described under [Rejected: bare-type binding](#rejected-bare-type-binding).
It is not on this feature's critical path and is scoped separately in
[Class Interfaces in IR](class-interfaces.md).

### Cleared: parameter annotations

Parameter annotations reach IR as `ConfigApplicationIr` built from resolved
symbols (`crates/dust_driver/src/lower.rs`), and only claimed symbols resolve.
A user type written directly on a parameter never survives lowering, which is
why `@Extract` exists as the claimed carrier.

`@Extract(BearerAuth)` carries a bare type reference, which lowers today as
`AnnotationValueIr::Member`, documented as "A member, type, or function
reference" (`crates/dust_ir/src/annotation.rs`). No new IR shape is needed.

### Cleared: structured workspace facts

Workspace analysis stores string sets, but the route plugin already serializes
structured facts as JSON into them
(`crates/dust_route_plugin/src/plugin/analysis.rs`). The only server feature
needing cross-file facts is schema generation for the documentation package,
which would follow that convention. No `dust_plugin_api` change is needed.

### Optional: doc comments in IR

IR carries no doc comments, so `summary` and `description` come from annotation
arguments. A later parser fact plus IR field would allow doc-comment fallback,
matching how FastAPI reads docstrings. Not required for any phase below.

## Annotation Surface

The complete list:

| Annotation | Target |
| :--- | :--- |
| `@Controller(path, ...)` | controller class (optional; a library of top-level handlers needs none) |
| `@GET` `@POST` `@PUT` `@PATCH` `@DELETE` `@HEAD` `@OPTIONS` | handler method or top-level function |
| `@FormUrlEncoded` `@MultiPart` | handler method or function, body media type |
| `@Extract(<extractor type>)` | handler parameter, custom extractor |
| `@Path` `@Query` `@Queries` `@RawQuery` `@Header` `@HeaderMap` `@Body` `@Field` `@Part` `@RawBody` `@State` `@Peer` | handler parameter, built-in extractor |

The vocabulary is deliberately the HTTP client's, not axum's spelling. `@Body()`
means the typed body on both sides, `@HeaderMap()` merges headers on both sides,
and `@FormUrlEncoded()`/`@MultiPart()` select the media type on both sides.
Phase 6 generates client and server from one declaration, which is only possible
if one annotation means one thing. Where axum's name and the client's name
disagree, the client wins; `@Headers({...})` stays reserved for the client's
method-level static headers.

Server verbs claim `dust_server::GET` and so on, distinct from the HTTP client's
`dust_dart::GET`. The plugin registry rejects duplicate symbol ownership
(`crates/dust_plugin_api/src/registry.rs`), and the two sides need different
argument sets regardless.

Discovery matches annotation short names
(`crates/dust_workspace/src/discover.rs`) and unions the sets across plugins, so
sharing short names with the client plugin is safe. A file cannot import both
`package:dust_dart/http.dart` and `package:dust_server/server.dart` without a
prefix, which is a Dart-level ambiguity and an accepted constraint.

### Two ways to declare handlers

A handler is a method on a `@Controller` class or a top-level function in a
library. The verb annotations target both, and the two produce the same thing:
a `Router` full of `Route` entries.

```dart
// class style: dependencies are fields
@Controller('/todos')
class TodoController with _$TodoController {
  TodoController(this._repo);

  final TodoRepo _repo;

  @GET('/{id}')
  Future<Result<Todo, NotFound>> get(
    @Extract(BearerAuth) AuthUser user,
    @Path() String id,
  ) =>
      _repo.find(user.id, id);
}
```

```dart
// function style: no class, so dependencies arrive through the request
part 'notes.g.dart';

@GET('/{id}')
Future<Result<Note, NotFound>> read(@Path() String id, @State() NoteRepo repo) =>
    repo.find(id);

@POST('/', status: 201)
Future<Note> write(
  @Extract(BearerAuth) AuthUser user,
  @State() NoteRepo repo,
  @Body() CreateNote input,
) =>
    repo.create(user.id, input);
```

| | Class | Functions |
| :--- | :--- | :--- |
| Prefix | `@Controller('/todos')` | none; the composition site supplies it |
| Dependencies | constructor parameters, held as fields | `@State()`, attached with `withState` |
| Generated entry point | `routes()` method on the mixin | a top-level function, `noteRoutes()` for `notes.dart` |
| Construction | `TodoController(repo)` at composition | nothing to construct |

Neither is preferred. A controller that holds three repositories reads better as
a class; a two-route module reads better as functions. The cost of the function
style is that dependencies become a runtime concern: missing state is
a 500 at request time, where a class controller simply could not have been
constructed without it.

The generated group carries an empty prefix in the function style, so mounting
is where the path comes from:

```dart
final notes = Router()
  ..merge(noteRoutes())
  ..withState(repo);

final app = Router()..nest('/notes', notes);
```

A **function**, not a getter, for two reasons that both bite:

* A `Router` is mutable and is sealed when its handler is read, so two servers
  in one isolate — every test file — each need their own. A getter that rebuilds
  on access gives that, but silently: `noteRoutes.withState(repo)` compiles,
  configures a throwaway, and answers **500 at request time** claiming the state
  was never attached. Written as a call, the same mistake reads as one.
* `serveCluster` takes a `RouterFactory`, which is `Router Function()`. A getter
  is not a value and cannot be passed, so a clustered application could not use
  the generated module at all.

Both styles land on `Router.module(...)`, which is why that factory is not
named `controller`.

### One annotation per handler

Everything that would otherwise be a stacked annotation is a verb argument.

```dart
@POST(
  '/',
  status: 201,
  summary: 'Create a todo',
  description: 'Creates a todo owned by the authenticated user.',
  tags: ['todos'],
  middleware: [RateLimit(perMinute: 30)],
)
Future<Todo> create(@Extract(TodosWrite) AuthUser user, @Body() CreateTodo input) =>
    _repo.create(user.id, input);
```

| Argument | Default |
| :--- | :--- |
| `path` (positional) | required |
| `status` | derived from return type |
| `summary`, `description` | none |
| `tags` | inherited from `@Controller` |
| `middleware` | controller's, appended |
| `operationId` | derived from method name |
| `deprecated` | `false` |
| `hidden` | `false` |

All argument shapes lower against today's IR: lists, maps, const constructor
invocations, and type references are already supported
(`crates/dust_ir/src/annotation.rs`).

> [!IMPORTANT]
> The full argument set is parsed and validated in Phase 1 even though nothing
> reads `summary`, `tags`, or `operationId` yet. Freezing the surface early
> means users never re-annotate when documentation ships.

### What Dust derives

FastAPI requires `response_model=` because Python return types are weak. Dart's
are not. Every argument the type system can answer is omitted:

| FastAPI argument | Dust source |
| :--- | :--- |
| `response_model` | static return type |
| request body schema | `@Body()` parameter type |
| parameter schemas and `required` | parameter types and nullability |
| `422` | body shape mismatch, and `Validate()` derive on the body type |
| `415`, `413` | body extractor presence, structural |
| `401`, `403` | rejection codes declared by the extractors in the signature |
| `400` | JSON syntax, path and query coercion, structural |

Failures outside the type system have nowhere to be declared until the
documentation package defines a `responses:` argument; a handler returning
`Result<T, E>` with `E` implementing `IntoResponse` already carries its own.

## Extractors

Modeled on axum: a handler declares what it needs as parameters, and the
framework produces those values from the request or fails with a typed
rejection. Axum resolves extractors through trait impls at compile time. Dart
has no equivalent dispatch, which is the gap Dust fills.

### One interface

```dart
/// Builds [T] from a request, or rejects it.
abstract interface class Extractable<T> {
  Future<Result<T, Rejection>> extract(Request request);
}
```

Dart has no static interface members, since `implements` constrains instance
members only, so the contract is an instance method and the extractor is an object
distinct from the value it produces. A `static fromRequest` could never be part
of an interface, so declaring one would be decoration the analyzer never checks.

The instance form pays for itself:

- the value type stays a plain data class with no framework coupling
- extractors take configuration, which axum needs newtypes to express
- `dart analyze` verifies `@override` and the method shape before `dust build`
  runs

Extractors that do not need the body use `RequestParts.of(request)` internally
for headers, method, and URI.

> [!NOTE]
> Axum splits this into `FromRequestParts` and `FromRequest` because Rust
> ownership forces the body to be consumed exactly once. For custom extractors
> Dust keeps one interface: the split would require Dust to determine which
> interface a class implements, a cross-file lookup this design avoids. The
> built-ins recover the guarantee without it; see
> [Body ordering is checked](#body-ordering-is-checked).

### Binding names the extractor type

```dart
@Extract(BearerAuth) AuthUser user,
```

The annotation argument is a type reference, not a value. Dust emits
`await const BearerAuth().extract(request)` from the type name alone and casts
the result to the parameter's declared type. An extractor declared as
`Extractable<SomethingElse>` fails to compile against an `AuthUser` parameter.

Rule: an extractor named this way needs a zero-argument `const` constructor.
Violations surface as an analyzer error at the generated call site; Phase 2 adds
a build diagnostic that checks the constructor list in `ClassIr` first.

Configuration is type-level, exactly as in axum, where `RequireScope<Write>`
encodes the scope in the type because Rust cannot pass a value at that position
either:

```dart
final class BearerAuth implements Extractable<AuthUser> {
  const BearerAuth({this.scope});
  final String? scope;

  @override
  Future<Result<AuthUser, Rejection>> extract(Request request) async { ... }
}

final class TodosWrite extends BearerAuth {
  const TodosWrite() : super(scope: 'todos:write');
}
```

```dart
@GET('/{id}')
Future<Result<Todo, NotFound>> get(@Extract(BearerAuth) AuthUser user, @Path() String id);

@POST('/')
Future<Todo> create(@Extract(TodosWrite) AuthUser user, @Body() CreateTodo input);
```

No top-level `const auth = BearerAuth()` declarations. Read and write scopes are
distinct types, so the difference is visible at each handler.

This removes an entire subsystem an earlier revision required: a discovery
marker annotation, a `dust_server.extractables.v1` workspace fact,
default-extractor and ambiguity rules with their diagnostics, a cross-file cache
dependency, and the `ClassIr.interfaces` engine change.

### Rejected: bare-type binding

`Future<Todo> create(AuthUser user)` with no annotation is the closest form to
axum's surface. It is rejected for this design:

| | Cost |
| :--- | :--- |
| Engine | `implements` clause in both parsers, `ClassIr.interfaces`, lowering, a workspace fact, a cache dependency |
| Diagnostics | ambiguity rules when two extractors produce one value type |
| Config | none possible. Scope cannot be expressed, and a second scoped extractor for `AuthUser` *is* the ambiguity case |

The engine cost buys a shorter call site and loses configuration. If
`ClassIr.interfaces` lands for its own reasons, revisit: bare-type binding
becomes cheap, and `@Extract(Type)` stays as the disambiguator.

### Built-ins, taken from axum

Built-ins ship in `dust_server` implementing the same `Extractable<T>`
interface. The annotation is sugar over a const extractor instance, so custom
extractors are not second-class. The set and the naming follow axum:

| axum | Dust | Notes |
| :--- | :--- | :--- |
| `Path<T>` | `@Path() String id` | key defaults to the Dart parameter name; `@Path('todo_id')` overrides |
| `Query<T>` scalar | `@Query('done') bool? done` | coerced; nullability decides required-ness |
| `Query<Vec<T>>` | `@Query('tag') List<String> tags` | `Uri.queryParameters` keeps only the last value for a repeated key, so a `List` parameter lowers to its own extractor |
| `Query<T>` struct | `@Queries() TodoFilter filter` | decoded through `Deserialize` |
| `RawQuery` | `@RawQuery() String? raw` | |
| `Json<T>` | `@Body() CreateTodo input` | JSON is the default media type |
| `Form<T>` | `@Body() LoginForm form` with `@FormUrlEncoded()` | reads the query on `GET`/`HEAD`, the body otherwise, matching axum |
| `Form<T>` field-wise | `@Field('email') String email` with `@FormUrlEncoded()` | mirrors the client's `@Field` |
| `Multipart` | `@Part('file') UploadedFile file` with `@MultiPart()` | typed per part, unlike axum's stream |
| `Bytes`, `String`, body stream | `@RawBody() Uint8List raw`, `String`, `Stream<List<int>>` | dispatch on the parameter type |
| `HeaderMap` | `@HeaderMap() Map<String, String> headers` | |
| `TypedHeader<T>` | `@Header('x-request-id') String? id` | |
| `State<S>` | `@State() NoteRepo repo` | attached with `withState`, keyed by type |
| `ConnectInfo<T>` | `@Peer() ConnectionInfo info` | `shelf.io.connection_info` |
| `Method`, `Uri`, `Version` | `RequestParts` parameter | one parameter beats four annotations |
| `Request`, `Parts` | bare `Request` / `RequestParts` parameter | passthrough |
| `State<S>` | controller constructor field | see Non-goals |
| `WebSocketUpgrade` | deferred | see [Deferred surfaces](#deferred-surfaces) |

Three names are server-only because the client has no use for them: `@RawBody`,
`@RawQuery`, `@State`, and `@Peer`. Everything else in the table is a name the
HTTP client already ships, carrying the same meaning.

`{id}` in a route path is rewritten to shelf's `<id>` during emission. A
`@Path()` parameter whose key has no matching path segment is a build
diagnostic.

`shelf_router` hands over path segments exactly as they appeared on the wire, so
`@Path()` percent-decodes before coercing (runtime-checked). `/files/a%20b`
yields `a b`, and malformed encoding is a 400 rather than a value carrying a
literal `%zz`.

### One body pass feeds every field (runtime-checked)

`@Field` and `@Part` are per-value annotations, but a body can only be read
once, so they cannot each be an extractor that reads it. The runtime splits the
two jobs: `FormExtractable` and `MultipartExtractable` read the body once and
produce a `FormMap` or `MultipartForm`, and each `@Field`/`@Part` parameter
lowers to a lookup on that value.

```dart
final $form = await const FormExtractable().extract(request);
if ($form case Err(:final error)) return error.intoResponse();
final $fields = ($form as Ok<FormMap, Rejection>).value;

final email = $fields.field<String>('email');
if (email case Err(:final error)) return error.intoResponse();
```

Lookups reject with 400 for a missing required value or a failed coercion, so
the status codes match the query and header extractors. This is why the
handler-level `@FormUrlEncoded()` and `@MultiPart()` annotations exist: they
tell the plugin which single body extractor to emit before the lookups.

### The body limit travels with the request (runtime-checked)

A body extractor's limit is fixed at build time, but the root `Router` is
written by hand at the composition site, so the two must meet. The root group
installs middleware writing `dust_server/body_limit` into the shelf request
context, and `readBody` prefers that value over its own. A limit configured at
composition therefore applies to generated code that never saw it.

### Parameter forms

```dart
Future<Todo> create(
  @Extract(TodosWrite) AuthUser user,
  @Body() CreateTodo input,
);

Future<List<Todo>> feed(@Extract(BearerAuth) Option<AuthUser> viewer);

Future<Response> remove(@Extract(BearerAuth) Result<AuthUser, Rejection> outcome);
```

`Option<T>` collapses a rejection to `None`. `Result<T, Rejection>` hands the
failure to the handler. Both are `dust_dart/fp.dart` types, and both wrap
built-ins as well as custom extractors.

`Option<T>` collapses client errors only (runtime-checked). A 5xx rejection
propagates, because those report a server-side fault: middleware that failed to
write a context value, or an adapter that supplied no connection information.
Collapsing them would turn a misconfiguration into a silently anonymous request,
which is exactly the bug `Option` is meant to make visible.

### Resolution precedence

1. Built-in parameter annotation.
2. `@Extract(<extractor type>)`.
3. Parameter type is `Request` or `RequestParts`.
4. Otherwise a diagnostic: the parameter needs an annotation.

### Body ordering is checked

Body-reading is a property of the annotation symbol, not of a user class, so the
plugin knows it from `ConfigApplicationIr` alone. `@Body`, `@Field`, `@Part`,
and `@RawBody` read the body; every other built-in reads parts only.

Two build diagnostics follow, with no cross-file work:

- at most one body-reading built-in per handler
- a body-reading built-in must be the last parameter

Axum gets this guarantee from `FromRequest` versus `FromRequestParts`; Dust gets
it from the symbol table. Custom extractors are exempt, because Dust cannot know
which side `BearerAuth` sits on, so the convention is documented and a double body
read surfaces as a `StateError` from `shelf` on the first request.

### Rules

- Extractors run in declaration order and short-circuit on the first `Err`.
- Extractors that depend on other extractors are out of scope. Middleware
  attached state plus `@State()` covers the common case.

## Rejections

Taken from axum, which splits body failure across four codes where a single 400
would lose information:

| Failure | Status | axum equivalent |
| :--- | :--- | :--- |
| Missing or wrong `content-type` | 415 | `MissingJsonContentType` |
| Malformed JSON syntax | 400 | `JsonSyntaxError` |
| Well-formed JSON, wrong shape | 422 | `JsonDataError` |
| Path segment fails coercion | 400 | `PathRejection` |
| Query fails coercion, or a required key is absent | 400 | `QueryRejection` |
| Body exceeds the configured limit | 413 | `LengthLimitError` |
| `Validate()` constraint fails | 422 | none |

422 therefore has two producers, shape mismatch and constraint failure, and
both carry field errors into the same `Rejection.unprocessable`, so clients see
one error format.

`Rejection` is a type in `dust_server` implementing `IntoResponse`, with
constructors for the standard client-error codes and a validation variant
carrying field errors. The body limit is a `Router` option, defaulting to
1 MiB.

Two protocol details the runtime handles, neither of which the generator has to
know about:

- A 401 carries `WWW-Authenticate`, which the HTTP specification requires and
  which a plain JSON error body omits. `Rejection.unauthorized` defaults the
  challenge to `Bearer`; an extractor authenticating differently passes its own.
- A known path reached with the wrong method answers 405 with `Allow`, not 404.
  `shelf_router` answers both cases with 404, so the router matches the
  request against the flattened route table itself before falling through.
  `HEAD` is listed in `Allow` wherever `GET` is, because `shelf_router` already
  serves `HEAD` from a `GET` route.

## Responses

Dispatch on the static return type, first match wins:

| Return type | Result |
| :--- | :--- |
| `Response` | passthrough |
| exposes `Response intoResponse()` | `intoResponse()` |
| derives `Serialize`, or a foreign type exposing `toJson()` | JSON, `status` or 200 |
| `List<T>`, `T` serializable | JSON array |
| `Result<T, E>`, `E` implements `IntoResponse` | branch on `Ok` / `Err` |
| `String` | `text/plain` |
| `List<int>` or `Uint8List` | `application/octet-stream` |
| `Stream<List<int>>` | streamed |
| `void` or `Unit` | 204 |
| anything else | diagnostic |

Detection reads the IR, never reflection — there is no `dart:mirrors` anywhere
in Dust, and a generator that needed it would defeat its own purpose.

For a Dust type the derive is the signal, and `serialize` / `deserialize` are the
verbs the generated code calls. `toJson` and `fromJson` are recognised **as
well**, structurally from `MethodIr`, so a model from outside Dust still works —
which is what `crates/dust_plugin_serde/src/analysis.rs` already does. Implementing
the `IntoResponse` interface from `dust_server` is the documented way to opt in
and keeps intent explicit, but the plugin matches on the method shape rather than
the interface
list, so no cross-file lookup is required.

### Uncaught exceptions (runtime-checked)

The generated handler wraps the handwritten call in `guard()`, which turns a
thrown `Rejection` into its declared status and anything else into an opaque
500. Guard clauses can therefore throw instead of threading a `Result` back.

The error and stack trace go to the `onError` callback passed to
`Router(onError:)`. That sink is scoped to a zone (`ServerErrors`),
because generated code is static and holds no reference to the group that
mounted it. One root per isolate is the assumption; a second root replaces the
sink when its handler is built.

500 is therefore possible on every route.

## Middleware

`middleware:` on `@Controller` and on a verb takes const expressions, so the
generated code needs a way to turn a const into a `shelf` `Middleware`:

```dart
abstract interface class RouteMiddleware {
  Middleware toMiddleware();
}

final class RateLimit implements RouteMiddleware {
  const RateLimit({required this.perMinute});
  final int perMinute;

  @override
  Middleware toMiddleware() => ...;
}
```

Emission is the same trick as extractors: Dust writes
`const RateLimit(perMinute: 30).toMiddleware()` from the lowered constructor
call and the analyzer checks the rest. `Router.layer` also accepts bare `shelf`
`Middleware` values at the composition site, for anything that does not need to
be expressible in an annotation.

Order is outermost-first: root group, then nested groups, then controller, then
verb.

## Composition

Route mounting is imperative, mirroring FastAPI's `include_router`, which is
also a runtime call rather than a decorator.

Controller paths are relative. A controller never knows where it is mounted, so
`/api/v1` is written once instead of repeated in every controller, and the same
controller can be mounted twice.

`handler` caches its result: the tree is walked once, and mounting after it
exists throws instead of returning a handler that silently ignores the new
routes. Building seals the whole mounted subtree, not just the group that was
built, since a nested group left unsealed would keep accepting includes the composed
handler can never see. `serveOpenApi` works on any group, not only the root:
the document is served at the mount-joined path, so a versioned group can carry
its own.

```dart
Router({Object? metadata, int? bodyLimit, void Function(Object, StackTrace)? onError});
Router.module({String prefix, List<Route> routes, Object? metadata});

void nest(
  String path,
  Router router, {
  String? prefix,
  List<String> tags = const [],
  List<Middleware> middleware = const [],
  Object? metadata,
});

Handler get handler;
```

Mapping to FastAPI:

| FastAPI | Dust |
| :--- | :--- |
| `APIRouter(prefix=, tags=)` | `Router()..nest(path, router)` |
| `app.include_router(r, prefix=, tags=)` | `group.include(r, prefix:, tags:)` |
| nested `include_router` | nested `include` |
| `dependencies=[Depends(auth)]` | `middleware:` for guards, parameter extractors when the handler needs the value |

There is no `@ServerApp` annotation. Controller discovery is automatic,
middleware is code, and anything else is an argument at the call site. An
app-level annotation would only have added ceremony.

## API documentation, deferred

OpenAPI is out of scope for this feature. It is the part with the least settled
design, the only part needing a new serde workspace fact, and the only part
whose output format is somebody else's specification. Shipping the server
without it costs nothing that cannot be added later.

Dart also has no library worth depending on for it. The survey, at the time of
writing:

| Package | Latest | Verdict |
| :--- | :--- | :--- |
| `open_api` | 2.0.1, September 2018 | Dart 2 only, abandoned |
| `openapi_spec` | 0.15.0, August 2025 | pre-1.0, 7 likes, near-zero adoption, spec-first |
| `swagger_parser`, `openapi_generator*`, `swagger_to_dart` | active | spec to client, the opposite direction |
| `conduit` | 7.0.0 | a whole framework, not a library |
| `shelf_swagger_ui` | 2.0.0, 85 likes | serves the UI from a finished document, complementary |

So whenever documentation does land it will be a separate package, `dust_openapi`
or similar, and `dust_server` carries only the seam it needs.

### The seam (runtime-checked)

Two things, both generic:

```dart
Router({Object? metadata});
Router.module({String prefix, List<Route> routes, Object? metadata});
void nest(String path, Router router);

List<MountedRoute> describe();
```

`metadata` is an opaque slot `dust_server` never reads. `describe()` walks the
mount tree and returns each route with the path the router serves and the
metadata of every group it was mounted through, outermost first, plus
`metadataOf<T>()` to pull the innermost of a type back out.

That is enough to rebuild everything the deleted emitter did, from outside:

```dart
// in a future dust_openapi package
extension on Router {
  Map<String, Object?> openApi({required String title, required String version}) {
    for (final route in describe()) {
      final doc = route.metadataOf<ApiDoc>();
      // ... build paths from route.method, route.path, doc
    }
  }
}
```

Adding it later is additive: a new package, a metadata type, and an extension
method. No change to `Router`, no change to generated controllers beyond
what they pass as `metadata`.

### What the annotations keep

`summary`, `description`, `tags`, `operationId`, `deprecated`, and `hidden`
stay on the verb annotations. They are plain strings, lists, and booleans with
no dependency on any spec type, and freezing them now means users never
re-annotate when documentation ships. `responses:` is the one argument that
left, because it needed a schema-reference type; adding a named parameter back
is not a breaking change.

### Costs of deferring

- No document at all until the separate package exists.
- The plugin will emit `metadata:` on generated controllers before anything
  reads it. Phase 5 decides that type, so until then generated code passes
  nothing.
- Duplicate `path` plus method is still caught, since `describe()` and
  `handler` share the same flattening and both throw on it.

## Testing

Two layers, both riding existing machinery:

- Plugin fixtures under `fixtures/`, asserting emitted `.g.dart` for each
  extractor form, response form, and diagnostic. Same shape as the other
  plugins' fixture suites.
- Generated route tests from Phase 3, reusing the `generateTest` machinery the
  HTTP client plugin already has: one test per route asserting method, path,
  status, and rejection codes against an in-process handler, with no socket.

`dust_server` itself carries unit tests for prefix normalization, `Router`
composition, `Rejection` encoding, and each built-in extractor.

### Auth extractor

The value type is plain Dart with no framework coupling:

```dart
// lib/src/auth/auth_user.dart
class AuthUser {
  const AuthUser(this.id, this.scopes);
  final String id;
  final List<String> scopes;
}
```

The extractor implements the interface, takes its configuration in the
constructor, and exposes each scope as a type:

```dart
// lib/src/auth/bearer_auth.dart
import 'package:dust_server/server.dart';

import 'auth_user.dart';

final class BearerAuth implements Extractable<AuthUser> {
  const BearerAuth({this.scope});

  final String? scope;

  @override
  Future<Result<AuthUser, Rejection>> extract(Request request) async {
    final raw = RequestParts.of(request).headers['authorization'];
    if (raw == null || !raw.startsWith('Bearer ')) {
      return const Err(Rejection.unauthorized('missing bearer token'));
    }

    final claims = await verifyJwt(raw.substring(7));
    if (claims == null) {
      return const Err(Rejection.unauthorized('invalid token'));
    }
    if (scope != null && !claims.scopes.contains(scope)) {
      return Err(Rejection.forbidden('requires scope $scope'));
    }

    return Ok(AuthUser(claims.subject, claims.scopes));
  }
}

final class TodosWrite extends BearerAuth {
  const TodosWrite() : super(scope: 'todos:write');
}
```

### Controller

```dart
// lib/src/api/todo_controller.dart
import 'package:dust_server/server.dart';

import '../auth/auth_user.dart';
import '../auth/bearer_auth.dart';
import '../errors.dart';
import '../models/create_todo.dart';
import '../models/todo.dart';
import '../repo/todo_repo.dart';

part 'todo_controller.g.dart';

@Controller('/todos', tags: ['todos'])
class TodoController with _$TodoController {
  TodoController(this._repo);

  final TodoRepo _repo;

  @GET('/', summary: 'List todos')
  Future<List<Todo>> list(
    @Extract(BearerAuth) AuthUser user,
    @Query('done') bool? done,
  ) =>
      _repo.list(user.id, done: done);

  @GET('/{id}', summary: 'Fetch one todo')
  Future<Result<Todo, NotFound>> get(
    @Extract(BearerAuth) AuthUser user,
    @Path() String id,
  ) =>
      _repo.find(user.id, id);

  @POST('/', status: 201, summary: 'Create a todo')
  Future<Todo> create(
    @Extract(TodosWrite) AuthUser user,
    @Body() CreateTodo input,
  ) =>
      _repo.create(user.id, input);

  @DELETE('/{id}', status: 204, summary: 'Delete a todo')
  Future<void> remove(
    @Extract(TodosWrite) AuthUser user,
    @Path() String id,
  ) =>
      _repo.remove(user.id, id);
}
```

Reads and writes use different scopes, and the difference is visible at each
handler rather than inferred from a registration elsewhere. `@Body()` is last,
which the body-ordering diagnostic enforces.

The statuses `create` can answer with, none of them written by hand:

| Code | Source |
| :--- | :--- |
| 201 | `status: 201` |
| 400 | malformed JSON |
| 401, 403 | `TodosWrite` rejections |
| 413 | body limit |
| 415 | missing `application/json` |
| 422 | shape mismatch, or `Validate()` on `CreateTodo` |
| 500 | uncaught exception |

For `get`, 404 comes from `NotFound` in the `Result` return type.

### Generated output

Sketch of `todo_controller.g.dart` for the `create` route:

```dart
mixin _$TodoController {
  Future<List<Todo>> list(AuthUser user, bool? done);
  Future<Result<Todo, NotFound>> get(AuthUser user, String id);
  Future<Todo> create(AuthUser user, CreateTodo input);
  Future<void> remove(AuthUser user, String id);

  Router routes() => Router.module(
        prefix: '/todos',
        routes: [
          Route('GET', '/', _$handleList),
          Route('GET', '/<id>', _$handleGet),
          Route('POST', '/', _$handleCreate),
          Route('DELETE', '/<id>', _$handleRemove),
        ],
      );

  Future<Response> _$handleCreate(Request request) async {
    final $user = await const TodosWrite().extract(request);
    if ($user case Err(:final error)) return error.intoResponse();
    final user = ($user as Ok<AuthUser, Rejection>).value;

    final $input = await const JsonExtractable<CreateTodo>(CreateTodo.deserialize)
        .extract(request);
    if ($input case Err(:final error)) return error.intoResponse();
    final input = ($input as Ok<CreateTodo, Rejection>).value;

    if (input.validate() case Invalid(:final errors)) {
      return Rejection.unprocessable(errors).intoResponse();
    }

    try {
      final result = await create(user, input);
      return Response(
        201,
        body: jsonEncode(result.serialize()),
        headers: const {'content-type': 'application/json'},
      );
    } on Rejection catch (rejection) {
      return rejection.intoResponse();
    } catch (error, stack) {
      ServerErrors.report(error, stack);
      return Rejection.internal().intoResponse();
    }
  }
}
```

Straight-line code. No reflection, no runtime registry, every type static.

Two casts are load-bearing. `as Ok<AuthUser, Rejection>` is where the analyzer
confirms that `TodosWrite` really does produce an `AuthUser`; Dust emits it from
the parameter's declared type without knowing anything about the extractor. The
`const TodosWrite()` call is where the analyzer confirms the zero-argument const
constructor exists.

### Request lifecycle

For `POST /api/v1/todos`:

1. Root group middleware runs in declaration order: `Cors`, `logRequests`.
2. The composed router matches the mounted prefix and dispatches to
   `_$handleCreate`.
3. Extractors run in declaration order. `TodosWrite` returns `Err`,
   short-circuiting to 401 or 403.
4. The body extractor checks `content-type` (415), the size limit (413), parses
   (400), and decodes into the type (422).
5. `validate()` returns 422 with field errors on failure.
6. The handwritten handler body runs, guarded for 500.
7. Response dispatch encodes the result as 201 JSON.

## Contracts

Phase 6 generates a Dio client and a server controller from one declaration.
The value is not saved keystrokes; it is that a path typo, a renamed query key,
or a changed request type becomes a compile error on both sides at once.

```dart
// package:todo_api/contract.dart, depended on by client and server
@HttpContract(baseUrl: 'https://api.example.com', tags: ['todos'])
abstract interface class TodoApi {
  factory TodoApi(Dio dio, {String? baseUrl}) = _$TodoApi;

  @GET('/todos/{id}', summary: 'Fetch one todo')
  Future<Todo> get(@Path() String id);

  @POST('/todos', status: 201)
  Future<Todo> create(@Body() CreateTodo input);
}
```

One declaration, two outputs:

| Output | Shape |
| :--- | :--- |
| `_$TodoApi` | the Dio client the HTTP client plugin already emits |
| `_$TodoApiServer` | a controller mixin whose generated handlers call the same method signatures |

The server side is applied by implementing the contract:

```dart
class TodoController with _$TodoApiServer implements TodoApi {
  TodoController(this._repo);
  final TodoRepo _repo;

  @override
  Future<Todo> get(String id) => _repo.find(id);
}
```

`implements TodoApi` is what makes the analyzer enforce agreement: a signature
that drifts from the contract fails to compile in the server package.

### Server-only parameters

A contract method's signature is the wire signature, so parameters the client
cannot supply are marked and skipped during client emission:

| Annotation | Client | Server |
| :--- | :--- | :--- |
| `@Path` `@Query` `@Queries` `@Header` `@HeaderMap` `@Body` `@Field` `@Part` | sends | extracts |
| `@Extract` `@State` `@Peer` | omitted from the client signature | extracts |
| `Request` `RequestParts` | rejected by a diagnostic | extracts |

Authentication is the common case, and omitting it from the client is correct:
the client sends a token through a Dio interceptor, while the server turns that
token into an `AuthUser`. The two are not the same value and should not share a
parameter.

### Argument divergence

| Argument | Consumer |
| :--- | :--- |
| `baseUrl`, `headers`, `parseThread`, `target` | client only |
| `status`, `middleware`, `hidden` | server only |
| `path`, verb, `summary`, `description`, `tags`, `operationId`, `deprecated` | both |

A client-only argument on a contract is not an error; the server plugin ignores
it, and vice versa. Only a *conflict*, two paths for one method, is
impossible by construction, which is the point.

### Symbol ownership

`@HttpContract` is one symbol and the registry rejects duplicate ownership
(`crates/dust_plugin_api/src/registry.rs`), so one plugin must claim it and
emit both sides. `dust_server_plugin` claims it and takes a crate dependency on
`dust_http_client_plugin` for the client half.

That requires the client plugin's emission to be callable as a module rather
than only from its own `DustPlugin` entry point. Today it is organized as
`parse/`, `validate/`, `emit/`, `plugin/`
(`crates/dust_http_client_plugin/src/`), so the refactor is a visibility change
plus a stable entry function, not a rewrite. Scope it as the first task of
Phase 6.

### Costs

- The contract package is a third package in the dependency graph, depended on
  by both client and server. Model types live there, so they must derive
  `Serialize` *and* `Deserialize` even where one side needs only one direction.
- `Result<T, E>` returns are server-only in Phase 6. The client would need to
  map a status code back to `E`, which is a decoder the contract does not carry
  yet. Contract methods return `Future<T>` and the client throws, as it does
  today.
- A contract cannot use the two sides' import-prefix escape hatch: the file
  imports `package:dust_server/server.dart` for the annotations, so the client
  package inherits a `shelf` dependency it does not use. Splitting the
  annotation set into a third `dust_http_annotations` package would fix it and
  is the open question below.

## Phases

| Phase | Scope | Exit criteria |
| :--- | :--- | :--- |
| 0 | Symbol-ownership spike. Package and crate skeletons, `dust_ir/src/server.rs`, registry entry. No parser, resolver, or IR work. | Server and client plugins coexist; discovery finds both. |
| 1 | `@Controller` and verbs with the full argument set, for both class and top-level-function handlers. `@Path`, `@Query`, `@Queries`, `@Header`, `@HeaderMap`, `@Body`. Response dispatch for JSON, `void`, `Response`. Path syntax rewrite and the missing-path-key diagnostic. | Todo controller serves GET and POST. |
| 2 | `@Extract(Type)` glue emission, zero-argument const-constructor diagnostic, `Option` and `Result` unwrapping, ordering, parameter diagnostics. | `BearerAuth` and `TodosWrite` both work. |
| 3 | Full axum rejection taxonomy including 413 and 415. `@FormUrlEncoded`, `@MultiPart`, `@Field`, `@Part`, `@RawBody`, `@RawQuery`, `@State`, `@Peer`. `status`, `Result<T, E>` returns, streams, bytes, text, `Validate` to 422, 500 guard. Body-ordering diagnostics. | Full todo controller; every row of the rejection table covered by a fixture. |
| 4 | `Router`, `include`, prefix normalization, `RouteMiddleware` emission, middleware composition, body limit, `onError`. Runtime library only, no driver work. | `bin/server.dart` runs end to end. |
| 5 | `metadata:` emission on generated controllers, and whatever workspace facts the documentation package needs. Documentation itself ships separately. | A `describe()` walk recovers every route with its metadata. |
| 6 | `@HttpContract`. Factor the client plugin's emission into a callable module, claim the symbol in `dust_server_plugin`, emit `_$TodoApi` and `_$TodoApiServer`, server-only parameter rules. | A shared contract package where a path change breaks both sides at compile time. |

Route-mapping test generation rides along from Phase 3 using the `generateTest`
machinery the HTTP client plugin already has.

## Deferred surfaces

Named so they are not rediscovered as gaps:

| Surface | Reason |
| :--- | :--- |
| WebSocket upgrade | `ws()` is a `MethodRouter` written by hand; a second handler shape does not fit the request-response contract |
| Server-sent events | `Stream<List<int>>` covers the transport; a typed `Stream<T>` SSE return needs its own response row |
| Static file serving | `staticFiles` mounts as a plain handler through `mount()`; nothing for the generator to emit |
| Content negotiation beyond JSON | one media type per body keeps extractors simple |
| Extractor-to-extractor dependencies | attached state plus `@State()` covers the real cases |

## Open Questions

None outstanding. The runtime was built first so the design could be checked
against working code, and every question that blocked the generator is answered
below.

## Deferred

- **Moving the shared annotations to a `dust_http_annotations` package.** The
  motivation stands — a Phase 6 contract package should not drag `shelf` into
  client-only consumers — but the split is not being made yet. Revisit when a
  contract package actually exists to be dragged into.

## Resolved

- **No `shelf_router` escape hatch is needed.** The question was how non-Dust
  routes get served, static files above all. `mount(path, handler)` answers it:
  it hands a subtree to any `shelf` `Handler`, which is what `staticFiles`
  already uses, and `example/static_files.dart` serves a single-page build
  through it. `shelf_router` stays a **dev** dependency, as the conformance
  oracle in `test/router/conformance/`, and nothing in `lib/` imports it.

- **`metadata` stays untyped, deliberately, so OpenAPI can land later.** The
  question was what type generated controllers should pass. The answer is that
  the runtime does not get to know: `Router` takes `Object?`, `describe()` hands
  back `List<Object>`, and `metadataOf<T>()` lets a consumer pull out its own
  type and ignore the rest. Naming a type in `dust_server` would drag a
  documentation format into the runtime, which is the coupling the slot exists to
  avoid.

  Until a documentation package defines one, generated controllers pass nothing.
  That costs only the document itself: adding it later is a new package, a
  metadata type, and an extension method — no change to `Router`, and one extra
  argument on generated controllers.

  What `describe()` already gives such a package: every route with its method,
  its path with `{name}` placeholders intact, and the metadata of every router it
  was mounted through, innermost first. What it does **not** give, and what an
  OpenAPI generator would take from the IR at build time instead: parameter
  types, request and response schemas, and status codes. `describe()` is runtime
  introspection of the route table, not a schema source.

  The verb annotations already carry everything that needs no spec type —
  `summary`, `description`, `tags`, `operationId`, `deprecated`, `hidden` — frozen
  now so nobody re-annotates when documentation ships. `responses:` is the one
  argument that left, because it needed a schema-reference type; adding a named
  parameter back is not a breaking change.

- **A nullable parameter rejects a malformed value.** The runtime settled this
  by behaving: a nullable type makes a value *optional*, not *forgiving*. Absent
  is `null`; present and uncoercible is a **400**, which matches axum and is
  stricter than most Dart HTTP code. `example/optional_extraction.dart` shows the
  three levels side by side, and its tests assert that `?page=x` is a 400 while
  `?page=` absent defaults cleanly. `optional(...)` is the opt-in that swallows
  both — and the example says plainly that it hands a client with a bug silence
  and page one.

- **Validation uses the built-in `Validate()` derive.** The generator does not
  define a validation mechanism of its own: it emits `@Derive([Validate()])` on
  the request model and calls `validBody`, which runs the generated `validate()`
  and answers **422** with per-field errors. That path is already proven by
  `example/validation_422.dart` — every broken rule reported at once, and a shape
  failure landing on the same status and body shape as a rule failure, so a
  client writes one error renderer.

  Whether those constraints are *also* published as a workspace fact for the
  documentation package is a separate question about the doc package, not about
  how validation runs, and it does not block the generator.

- **Method name: `extract`, not `fromRequest`.** `implements` cannot constrain
  statics in Dart, so the contract must be an instance method, and `extract`
  reads better on an instance.
- **Double body reads.** Built-ins are known by symbol, so both the
  at-most-one and the must-be-last rules are build diagnostics. Custom
  extractors remain by convention.
